# Claude Code実装指示書：YOLO検出結果の回帰テスト基盤

## 1. 背景と目的

YOLOなどの物体検出モデルに追加学習を行った際、全体のmAPなどが改善していても、以前検出できていた特定の物体が検出できなくなる可能性がある。

通常のソフトウェア開発では、実装変更による振る舞いの破壊を回帰テストによって検出する。

本プロジェクトでは、その考え方を物体検出モデルにも適用する。

**目標は、同じ動画・画像に対する学習前後の検出結果を比較し、どのフレームのどの検出が変化したのかを再現可能な形で記録・検証できる仕組みを作ること。**

将来的には「どのような学習データを追加した結果、どの検出能力が改善・悪化したのか」の分析に発展させたい。

ただし、今回はそのための最小基盤を作る。

## 2. 最重要の設計方針

### 2.1 モデルそのものではなく、推論結果を比較する

比較エンジンはモデルの重みを直接扱わない。

入力は以下とする。

- 学習前モデルの推論結果JSON
- 学習後モデルの推論結果JSON
- 必要に応じて、人間が確認した正解アノテーション

推論の実行と、結果の比較は分離すること。

### 2.2 差分検出と正誤判定を分離する

**差分検出（Snapshot Diff）**

正解ラベルがなくても実行できる。

- 新しく出現した検出
- 消失した検出
- BBoxの位置・サイズの変化
- Confidenceの変化
- クラスの変化

を検出する。

**回帰判定（Regression Evaluation）**

正解アノテーションがあるフレームに限り、期待する検出が維持されているかを判定する。

- PASS → PASS：維持
- FAIL → PASS：改善
- PASS → FAIL：回帰
- FAIL → FAIL：未改善

差分があること自体を「改善」「悪化」と判定してはいけない。

また、正解ラベルがないフレームを品質評価の集計対象にしてはいけない。

### 2.3 動画はフレーム単位で扱う

動画全体を一つの比較対象として扱うのではなく、同じ動画から抽出された対応するフレームを比較する。

フレーム番号またはタイムスタンプで対応づける。

フレームの抽出条件は固定すること。

- 元動画の識別情報
- フレーム番号
- タイムスタンプ
- 元動画のFPS
- フレームの幅・高さ

を保持する。

最初のバージョンでは、**同じ元動画を同じ条件で処理した結果のみ比較対象とする**。

FPSの異なる動画間の時刻同期や、別動画間のフレーム対応づけは対象外。

## 3. 技術構成

推論とフレーム画像の抽出はPython、比較・回帰判定・レポートはTypeScriptで実装する。両者は共通JSONスキーマ（5章）のファイルだけで受け渡し、互いのコードを呼び出さない。

### 3.1 Python側（推論・フレーム抽出）

- Python 3.11以上
- Ultralytics（YOLO推論用アダプター）
- OpenCV（動画フレームの読み込み・画像の書き出し）
- pytest（推論結果をスキーマに変換する処理のテスト）
- jsonschema（出力JSONが共通スキーマに適合するかのテスト。開発時の依存のみ）

CLIはTyperなどを使ってもよいが、依存関係は必要最小限にする。

### 3.2 TypeScript側（比較・回帰判定・レポート）

- Node.js 22以上、TypeScript
- zod（JSONの読み込み時の検証。共通スキーマの定義元を兼ねる）
- vitest（比較エンジン・回帰判定のテスト）
- React + Vite（静的レポートビューア）

比較ロジックはUltralyticsにもReactにも依存しない純粋な関数として実装する。CLIとビューアはその関数を呼び出すだけにする。

### 3.3 評価指標の実装

IoU、一対一の対応づけ、TP / FP / FN は、TypeScriptに定番のライブラリがないため自前で実装する。代わりに、10章のテストで正しさを保証する。一対一の対応づけの方式（貪欲法かハンガリアン法か）は、選んだ理由をADRに記録する。

数値の比較は、浮動小数点の誤差を考慮した許容誤差つきで行う。

## 5. 共通JSONスキーマ

モデルに依存しない形式で推論結果を保存する。

例：

```json
{
  "schema_version": "1.0",
  "source": {
    "path": "sample.mp4",
    "sha256": "<video-sha256>",
    "fps": 30,
    "width": 1280,
    "height": 720
  },
  "inference": {
    "model_id": "model-v1",
    "confidence_threshold": 0.25,
    "iou_threshold": 0.7,
    "image_size": 640
  },
  "frames": [
    {
      "frame_index": 100,
      "timestamp_ms": 3333.33,
      "detections": [
        {
          "class_id": 39,
          "class_name": "bottle",
          "confidence": 0.92,
          "bbox": [120, 80, 200, 340]
        }
      ]
    }
  ]
}
```

### スキーマ上の注意事項

- BBoxは `[x1, y1, x2, y2]` のピクセル座標に統一する。
- BBoxの座標系は元動画の解像度に合わせる。
- JSONのschema_versionを保持する。
- モデル名、推論閾値、入力サイズを記録する。
- クラスIDだけでなくクラス名も保持する。
- モデル間でクラス名とIDの対応が異なる場合を考慮する。
- 元動画のハッシュを記録し、別素材の結果を誤って比較しないようにする。
- 比較対象のフレーム集合が一致しない場合は、黙って欠損を無視せずエラーまたは明示的な警告とする。
- confidence閾値が異なる場合は比較の解釈が変わるため、原則として同一条件を要求する。
- JSONの数値配列を単純比較して差分判定しない。

## 6. 推論結果の生成

Python側で以下のようなCLIを提供する。

```bash
detection-regression-infer infer \
  --model models/before.pt \
  --video samples/test.mp4 \
  --output results/before.json \
  --imgsz 640 \
  --conf 0.25
```

推論は一度だけ実行し、結果をJSONとして保存する。

比較のたびにYOLOモデルを読み込んで推論する必要はない。

同様に、追加学習後のモデルで `after.json` を生成する。

動画の全フレームを処理できること。長い動画でも不要なフレーム画像をすべてメモリに保持しないこと。

フレームは先頭から順に読み込み、読み込んだ順の番号を `frame_index` とする。シークでフレームを取り出すと、コーデックによっては指定と別のフレームが返るため。9章のフレーム抽出も同じ読み込み方にそろえる。

なお、最初は短い動画や静止画像の集合で動作確認できればよい。

## 7. 検出結果の比較

TypeScript側のCLI例：

```bash
detection-regression compare \
  --before results/before.json \
  --after results/after.json \
  --output results/diff.json
```

### 7.1 BBoxの対応づけ

同一フレーム内で、学習前後の検出結果を対応づける。

クラスを考慮したBBoxのIoUを基本とする。

- 同じクラスかつIoUが設定閾値以上であれば対応候補とする。
- 一つの検出を複数の検出に対応づけない。
- 複数候補がある場合も一対一対応を保証する。
- 対応づけられなかった学習前の検出は「消失」候補。
- 対応づけられなかった学習後の検出は「出現」候補。

最初はIoUによる対応づけでよいが、実装上の制約をREADMEに記載する。

モデル間のクラス変更や大幅な位置変化は、必ずしも同一物体として対応づけられない可能性がある。その場合は、無理に同一視せず未対応として記録する。

### 7.2 比較する項目

対応づけられた検出について、以下を比較する。

- Confidenceの差分
- BBoxのIoU
- BBox中心座標の移動量
- BBoxの幅・高さの変化

閾値は設定可能にする。

検出結果に変化があっても、閾値以内なら同等として扱えるようにする。

### 7.3 差分JSON

各フレームについて、以下の分類を保存する。

- `unchanged`
- `appeared`
- `disappeared`
- `modified`

`modified`には変更項目と変更量を含める。

出力JSONには集計結果だけでなく、各検出のbefore/after情報を残すこと。

元のJSONと比較結果から、後から検証を再実行できる構成にする。

## 8. オプションの回帰判定

ここは差分比較エンジンとは独立した機能として、TypeScript側に実装する。

```bash
detection-regression evaluate \
  --before results/before.json \
  --after results/after.json \
  --annotations annotations/test.json \
  --output results/evaluation.json
```

正解アノテーションが存在するフレームだけを対象とする。

### 8.1 正解データ

テスト用のフレームごとに、期待するクラスとBBoxを定義できる形式にする。

最初は独自のシンプルなJSON形式でよい。

ただし将来的にYOLO形式やCOCO形式のラベルから変換できるよう、読み込み処理は分離する。

### 8.2 判定

各モデルの検出結果を正解BBoxと照合する。

- クラス一致
- IoU閾値以上
- 一対一対応

を基本として、TP / FP / FNを計算する。

同一フレームについてbefore/afterの判定を比較し、改善・回帰・維持・未改善を出力する。

正解が複数ある場合は物体単位で判定する。

### 8.3 評価の整合性

以下を保証する。

- 同じJSON同士を比較すれば差分はゼロ。
- 同じ条件での評価結果は決定的である。
- 検出の順序を変更しても比較結果が変わらない。
- 正解のない検出はTPにならない。
- 1つの正解BBoxに対して複数のTPを発生させない。
- 正解ラベルのないフレームをPASSとして扱わない。

## 9. 結果の可視化

初版では本格的なWebアプリや動画プレイヤーを作らない。

**差分があるフレームを中心とした静的HTMLレポート**を生成する。レポートはReact + Viteでビルドした静的ビューアとし、Webサーバーなしでローカルで開けるものにする。

レポートに含める項目：

1. 比較対象のモデル・推論設定
2. 対象動画・フレーム数
3. 差分が発生したフレーム数
4. 出現・消失・変更の件数
5. 差分が大きいフレームの一覧
6. フレームごとのbefore/after検出BBox
7. 正解ラベルがある場合は回帰判定

元動画から該当フレームの画像を抽出し、before/afterのBBoxを重ねて表示する。

全フレームの画像を書き出すのではなく、差分があるフレームやユーザーが指定したフレームのみを対象とする。

### 9.1 生成の流れ

1. TypeScript側の `compare` で `diff.json` を作る。
2. Python側の `extract-frames` で、`diff.json` に含まれる差分のあるフレームだけをPNGに書き出す。
3. TypeScript側の `report` で、ビルド済みのビューア、`diff.json` などの結果、抽出した画像を1つのフォルダにまとめる。

```bash
detection-regression-infer extract-frames \
  --video samples/test.mp4 \
  --diff results/diff.json \
  --output results/report/frames

detection-regression report \
  --diff results/diff.json \
  --evaluation results/evaluation.json \
  --frames results/report/frames \
  --output results/report
```

フレーム画像はPython側で書き出し、ブラウザの `<video>` では表示しない。`<video>` のシーク位置はフレーム単位で正確ではなく、BBoxを別のフレームに重ねてしまうため。

### 9.2 ローカルで開くための制約

`file://` で開いたページからは `fetch` でJSONを読み込めない。`report` は結果のJSONを `data.js`（`window.__REPORT__ = {...}` を代入するスクリプト）として書き出し、ビューアは `<script src="data.js">` で読み込む。画像は相対パスの `<img>` で参照する。

初版では動画タイムライン、リアルタイム再生、追跡ID、Webサーバーは不要。ビューアは結果を表示するだけにし、ビューアの中で比較や判定を計算し直さない。表示と `diff.json` の内容が食い違わないようにするため。

## 10. テスト

vitestで比較エンジンと回帰判定のテストを作成する。Python側は、Ultralyticsの推論結果を共通スキーマに変換する処理と、出力JSONがスキーマに適合することをpytestで確認する。

最低限、以下のケースを網羅する。

### 検出結果の対応づけ

- 完全一致したBBox
- 少し位置がずれたBBox
- IoUが閾値未満のBBox
- クラスの不一致
- beforeにしか存在しないBBox
- afterにしか存在しないBBox
- 同一クラスが複数存在するケース
- 同じBBoxに複数の検出が重複するケース

### JSON比較

- 同一JSONでは差分ゼロ
- 検出順序を変更しても結果が同じ
- Confidenceだけが変化した場合
- BBoxだけが変化した場合
- クラスが変化した場合
- 空の検出結果
- フレーム数の不一致
- 動画ハッシュの不一致
- スキーマバージョンの不一致

### 回帰判定

- PASS → PASS
- PASS → FAIL
- FAIL → PASS
- FAIL → FAIL
- 未アノテーションのフレーム
- 複数の正解BBox

テスト用のbefore/after JSONは手作業で設計し、期待結果を明示する。

YOLOの実モデルもPythonの環境もなくても、比較ロジックのテストが全て実行できること。

## 11. 実験計画

最初からキャップ野球の高速小物体検出を使わない。

まずはCOCOの既存クラス（例：bottle）を対象にする。

### Phase A：比較エンジンの検証

- 人工的な推論結果JSONを用意する
- 出現・消失・位置変化・Confidence変化を検出する
- vitestで評価ロジックの正しさを確認する
- HTMLレポートを生成する（フレーム画像の代わりに無地の画像を使ってよい）

この段階ではYOLOモデルもGPUもPythonも不要。

### Phase B：実際の動画で比較

- 数秒程度の動画を用意する
- 学習済みYOLO26nなどの小型モデルで推論する
- JSONを保存する
- 比較エンジンで処理できることを確認する
- 一部のフレームに正解BBoxを付けて回帰判定を検証する

動画全フレームに正解BBoxを付ける必要はない。

### Phase C：追加学習による回帰の検証

比較エンジンが完成した後に実施する。

- 同一の初期重みから学習する
- 通常データとノイズを含むデータで学習条件を比較する
- 学習前後で同一動画を推論する
- JSON差分を算出する
- 回帰したテストケースが存在するか調べる

最初は640px程度の軽量実験とする。

1280pxでの大規模な再学習は不要。

追加学習による回帰が必ず発生するとは限らないため、回帰を発生させること自体を成功条件にはしない。

学習データの追加が性能変化の原因であることを主張するには、別途対照実験が必要。

## 14. 実装時の進め方

まずリポジトリの状況を確認すること。

既存コードがある場合は、その構成と依存関係を尊重する。

最初から全機能を実装せず、以下の順番で進める。

1. JSONスキーマをzodで設計し、JSON Schemaを生成
2. 人工JSONによる比較エンジンをTypeScriptで実装
3. vitestで比較結果を保証
4. Ultralyticsの推論アダプターをPythonで追加し、出力をJSON Schemaで検証
5. 一部フレームの正解ラベル照合を追加
6. フレーム抽出と静的HTMLレポート（React + Vite）を実装
7. 実動画で動作検証
8. READMEと実験手順を整備

特に、**先に学習を始めたり、複雑なWeb UIを作り始めたりしないこと。**

設計上の重要な選択については、理由と却下した代替案を記録すること。既存プロジェクトにADRの仕組みがあれば、それに従う。なければ `docs/adr/` に置く。

最初のADRには、言語の分け方を記録する。

- 採用：推論とフレーム抽出はPython、比較・回帰判定・レポートはTypeScriptとReact。理由は、推論にはUltralyticsが必要な一方、比較以降はJSONを扱うだけで、既存の自作ツールと同じReact + Vite + TypeScriptの構成にそろえられるため。
- 却下：すべてPythonで実装する案。対応づけに `scipy.optimize.linear_sum_assignment` などの既存ライブラリを使える利点はあるが、レポートのUIを作りにくい。
- 受け入れた代償：IoUと対応づけを自前で実装すること（3.3節）、スキーマを2つの言語で扱うこと（4章の生成の仕組みで対処）。
